## 1. 为什么不再使用纯数字分支名

原来的 `V1 / V2 / V3` 适合快速备份，但不适合长期研究迭代。公平性推荐改造后续会包含很多方向：

- 后处理重排序参数实验
- 模型内 fairness loss 改进
- Top-K aware fairness loss
- 候选池构造方式改进
- 多数据集验证
- 多随机种子验证
- 论文表格与可视化输出
- 主模型替换或结构升级

如果只使用 `V2 / V3 / V4`，后面很难从分支名判断每个版本到底做了什么，也不方便回退、复现实验和写论文。

因此后续统一使用“版本号 + 阶段/主题 + 核心目的”的分支命名方式。

## 2. 分支命名规范

推荐格式：

```text
v{版本号}-{阶段或主题}-{核心改动}
```

示例：

```text
v1-fairness-foundation
v2-stage4-fairloss-scale
v3-topk-aware-fairloss
v4-multidataset-validation
v5-paper-table-export
v6-conve-replacement-study
```

命名原则：

- `v{版本号}`：保留版本顺序，方便知道先后关系。
- `{阶段或主题}`：说明属于哪条研究线。
- `{核心改动}`：说明该分支主要解决什么问题。
- 尽量控制在 3 到 5 个英文短词内。
- 不再新建只有 `V2 / V3 / V4` 这种纯数字分支。

## 3. 当前 V1 的语义化命名

当前 `V1` 实际上不是一个简单备份版本，而是公平性推荐改造的基础版本。

建议重命名为：

```text
v1-fairness-foundation
```

含义：

## 5. Git 忽略策略

后续上传 GitHub 时，不再上传运行结果、大数据目录和临时文件。

当前 `.gitignore` 已经排除：

```text

Code/Data_Fin/
*.log
__pycache__/

```

含义：

- `Code/runs/`：模型训练结果、checkpoint、score 文件、实验 summary，不上传。

- `*.log`：运行日志不上传，避免再次出现大日志污染仓库。

注意：

- `Code/Data_Fin/` 已从 Git 跟踪中移除，但本地文件仍然保留。

## 6. 分支记录文档

仓库根目录新增：

```text
BRANCH_HISTORY.md
```

这个文件作为长期分支总账。每次创建新分支或完成一个阶段，都需要更新它。

每个分支至少记录：

| 字段 | 说明 |
|---|---|
| 分支名 | 语义化分支名 |
| 原分支名 | 如果由旧命名改来，记录旧名称 |
| 基于哪个分支 | 如 `v1-fairness-foundation` |
| 创建时间 | 分支创建时间 |
| 状态 | `planning/running/completed/abandoned` |
| 改造目标 | 这一版要解决的问题 |
| 核心代码改动 | 改了哪些模块 |
| 实验内容 | 数据集、seed、参数、命令 |
| 结果位置 | 本地 `Code/runs` 路径 |
| 最新提交 | commit hash |
| 当前结论 | 有效、无效、待继续验证 |
